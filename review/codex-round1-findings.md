## A. FIDELITY

- [SEVERITY: medium] A1 — “Does not predict task success” turns an uncontrolled benchmark comparison into a general law. The paper supports a minimalist starting point, but explicitly leaves matched-condition performance unresolved — `review/paper-2609.00006.txt`, §13.4 Axis 1: “Whether the production scaffolding produces measurable improvements on the same benchmark under matched conditions is an open question that this study does not answer.”

- [SEVERITY: medium] A1; anatomy “Tools & actions”; decision rule 4 — Starting with four tools matches Listing 3, but contradicts the cited Recommendation 3. This is a chosen scaffold default, not agreement between the paper’s recommendation and example — `review/paper-2609.00006.txt`, §16.3: “Begin with just a bash tool. Add more tools only in response to observed failure modes”; §16.10 instead supplies a “four-tool surface.”

- [SEVERITY: medium] A2 — The benchmark and ablation numbers are accurate, but “Structural fixes beat prose fixes” overgeneralizes one ablation. The guide’s successful intervention explicitly included replacing the system prompt — `review/paper-2609.00006.txt`, §15.5 calls the result “suggestive evidence that structural scaffold is more portable than prose-level prompt strategy”; `review/guide-v260411.txt`, §10: “The original system prompt was vague guidance. It was replaced with a mandatory four-stage framework.”

- [SEVERITY: high] A3 and A8 — “Conversation memory ceiling … is SQLite FTS5” and “None uses embeddings as primary substrate” present an internally inconsistent paper claim as settled. Observation 5 supports that wording, but the detailed retrieval audit and Observation 9 qualify it with a default hybrid exception — `review/paper-2609.00006.txt`, §13.2, approximately lines 2922–2927: “OpenClaw’s default memory plugin (memory-core) now runs a hybrid sqlite-vec KNN + FTS5/BM25 search with embeddings on by default.” Table 13 repeats this exception.

- [SEVERITY: medium] A3; decision rule 9; §5 vector-RAG prohibition — The document removes Recommendation 16’s exception for demonstrated semantic **code** retrieval, while transferring its experimental requirement to conversation recall with a different comparator. Those are substantive policy choices, not faithful restatements — `review/paper-2609.00006.txt`, §16.9, Recommendation 16: “If you believe your domain needs semantic code retrieval, first prove it improves over ripgrep+tree-sitter on a held-out task set before adding the infrastructure.”

- [SEVERITY: medium] A6 — “Agents do not verify themselves” converts a common failure into an impossibility and conflates unsupported self-assessment with tool-grounded verification. The cited guide explicitly advocates the latter — `review/guide-v260411.txt`, §08: “give Claude a way to verify its own work”; §06 describes agents comparing screenshots and runtime logs, then deciding whether a change was correct. Neither source establishes verification’s universal “highest-value” ranking.

- [SEVERITY: medium] A7; §7 weeks 7–10 — Near-universal deferred loading is established for **skills**, not tools generally, and the approximately 15 threshold is a tool-count recommendation, not a skill-count threshold — `review/paper-2609.00006.txt`, §12.5: “eight of the nine adopters now load only skill metadata eagerly”; §14.5: “Deferred tool loading went from one system to three”; Recommendation 4 says “When your tool count exceeds ∼15.”

- [SEVERITY: medium] A9 — “In-process in 8/9 systems” drops a material qualification from the cited Observation 11. The paper’s conclusion repeats the shortened claim, but its detailed account explicitly includes cross-process exceptions — `review/paper-2609.00006.txt`, §13.3: “eight of nine multi-agent systems still use in-process primitives **or, where they cross processes, something other than the standard protocols**”; Table 14 identifies Pi’s OS processes and Hermes’s subprocess swarm.

- [SEVERITY: low] A9 — “Cheapest useful multi-agent pattern” has no supporting cost comparison. The guide recommends simplicity and practicality, not a measured cost minimum — `review/guide-v260411.txt`, §17: “The most practical pattern may also be the simplest: one writes, one reviews.”

- [SEVERITY: medium] A11 — The exact-match/frontier versus fuzzy/weaker split reproduces Recommendation 5, but treats that coarse recommendation as exhaustive despite contrary detail in the cited Observation 4. Model-specific editing dialects cannot be reduced entirely to model strength — `review/paper-2609.00006.txt`, Observation 4: “GPT-family models get a Codex-style patch DSL and lose the string-replacement tools entirely”; Table 7 also lists Codex’s patch DSL.

- [SEVERITY: medium] §2 anatomy introduction; “Tools & actions” and “Extensibility” rows — The mapping introduces “Capability” as one of G’s five layers, producing six distinct G-layer labels across the table. G discusses capability in §16, but it is not a component in the cited §04 taxonomy — `review/guide-v260411.txt`, §04 names “Instructions,” “Constraints,” “Feedback,” “Memory,” and “Orchestration.”

- [SEVERITY: medium] §2 “Feedback (G only)” row — Feedback is only absent as a separately named **canonical subsystem** in P; it is not absent from P’s anatomy or recommendations. The current label obscures an important overlap — `review/paper-2609.00006.txt`, §6.3 describes the reflection loop; Table 12 defines “Outer Verification Loop” as a “Scaffold-level judge/guard validating completion, outside the turn loop.”

- [SEVERITY: high] Decision rule 1 — “Otherwise instruction file” incorrectly excludes costly but reversible actions from mechanical enforcement. The cited section explicitly puts a reversible action on the constraint side — `review/guide-v260411.txt`, §15, approximately line 2171: “Pushed to main? Revertable but painful — constraint.”

- [SEVERITY: low] A9 citation — G §08 describes architectural simplification generally, but the explicit removal of Sprints and per-Sprint evaluation is in G §05 and §17. The citation should point there — `review/guide-v260411.txt`, §05, approximately line 756: “Sprint mechanism removed, context reset removed, Evaluator went from per-Sprint evaluation to a single end-of-run evaluation.”

## B. OMISSIONS

- [SEVERITY: high] A4; anatomy “Safety & permissions”; §7 — The developer-tool approval model is missing: read-only planning, ordinary approval, bypass mode, and scoped permissions. Caps plus a catastrophic-command floor do not answer who authorizes ordinary consequential actions — `review/paper-2609.00006.txt`, §16.6, Recommendation 9: “implement a three-mode approval system (PLAN / DEFAULT / YOLO) with permission-scope patterns.”

- [SEVERITY: high] A6; §4 operating loop — Verification assumes a specification exists but never establishes how requirements become testable acceptance criteria before implementation. This omits the central contract mechanism in the Anthropic case — `review/guide-v260411.txt`, §08: “the Generator proposes an implementation plan and success criteria, the Evaluator reviews whether those criteria are testable, both iterate until agreement, then coding begins”; §06 separately warns that internal quality checks can miss “functional and behavioral correctness.”

- [SEVERITY: high] A6, A13; §7 exit criterion — Final human accountability is missing. Human confirmation of harness regressions is not a release-review policy, and a fresh AI reviewer does not supply the practitioner’s understanding of what ships — `review/guide-v260411.txt`, §07: “I’m not shipping code I don’t understand”; §09: “every AI-generated PR still requires human review” and “Stripe doesn’t let AI auto-merge anything.”

- [SEVERITY: high] A4, A8, A10; anatomy safety row — Security focuses on dangerous commands and third-party skills, omitting the broader untrusted-content boundary and protection of credentials and memory writes — `review/paper-2609.00006.txt`, §10.7 describes “promptware scanning of context files, memory writes, MCP tool descriptions, and skill installs”; §10.3 wraps repository content in `<UNTRUSTED_CONTENT>`; §8.5 describes environment scrubbing of provider credentials.

- [SEVERITY: medium] Anatomy “LLM integration” row — A quirk table is named without the capabilities it must preserve or the maintenance obligation it creates. Recommendation 2 and Observation 2 emphasize provider-specific caching, reasoning controls, and explicit portability choices — `review/paper-2609.00006.txt`, §16.2: “cache breakpoints, thinking tiers, and reasoning effort are reachable from an abstraction—the cost is a maintained per-provider conditioning layer, paid once and centrally.”

- [SEVERITY: medium] Anatomy “Memory & context” row; decision rule 3 — Root-to-cwd discovery and subdirectory files omit Recommendation 6’s user/extension scopes, neighboring filename conventions, and just-in-time injection when tools enter a subtree — `review/paper-2609.00006.txt`, §16.5: “Auto-discover hierarchical Markdown context files at project, user, and extension scopes—and read your neighbors’ filenames too”; “surface nested files just-in-time when tools touch their subtree.”

- [SEVERITY: medium] A10, A11; anatomy “Tools & actions” row — Tool count, consolidation, and edit matching receive rules, but tool usability does not: schemas, parameter examples, actionable errors, and tool testing are missing — `review/guide-v260411.txt`, §16: “Investing effort in tool documentation and testing matters as much as investing in UI design”; its checklist requires “clear parameter descriptions and examples” and errors that explain what went wrong.

- [SEVERITY: medium] §4 trace step; §7 plan — Environmental unfamiliarity is listed as a failure class without the guide’s corresponding intervention: making the actual runtime environment discoverable at startup. Reproducibility alone does not give the agent this information — `review/guide-v260411.txt`, §10: “LocalContextMiddleware auto-injects environment information when the agent starts,” including directory structure and available tools.

- [SEVERITY: medium] A1; §6 reference scaffold — There is no initial decision about whether a task needs an agent at all. A first-principles document should distinguish a single model call or fixed workflow from an open-ended tool loop — `review/guide-v260411.txt`, §17: “If a single LLM call can solve it, don’t use an agent.”

- [SEVERITY: medium] Anatomy; A13 operating policy; §7 — Persistence, resume, checkpointing, and rollback have no explicit design position, although recovery is a stated spending priority. Mentioning Stripe’s rollback infrastructure as evidence does not establish a recovery policy — `review/paper-2609.00006.txt`, §2.3 identifies the shared “session substrate (transcripts, persistence, resume/fork)”; Table 11 lists filesystem checkpoints and restoration; `review/guide-v260411.txt`, §09 relies on “blue-green deployment supporting rapid rollback.”

## C. INTERNAL CONSISTENCY

- [SEVERITY: high] A5 and decision rule 2 versus A4 and A13 — “Add a rule only after an observed failure” conflicts with enforcing catastrophic boundaries and engineering prerequisites before use. The document needs an explicit exception for known safety and quality requirements — `review/guide-v260411.txt`, §05 lists “Critical safety and quality red lines” among rules to keep; §15 says architectural constraints “must come first.”

- [SEVERITY: high] A6 and A9 operating instructions versus A9 heading and decision rule 7 — Fresh-context writer/reviewer work is explicitly prescribed, while multi-agent use is permitted only for breadth-first exploration. Review is not that phase, so the document both requires and prohibits its own verification pattern — `review/guide-v260411.txt`, §17 separately recommends “Writer/Reviewer dual sessions” for “Write code + review code.”

- [SEVERITY: medium] §2 memory upgrade trigger versus decision rule 8 and §7 exit criterion — The anatomy makes cross-session memory conditional on need and allows deliberate absence; the rule and exit criterion require every harness to have a bounded, frozen memory file and write path. This also collapses the distinct governance designs acknowledged in A8 into Hermes-style storage — `review/paper-2609.00006.txt`, §9.6: “Pi and Mini-SWE-Agent deliberately persist nothing beyond the session substrate.”

- [SEVERITY: high] §7 weeks 3–13 versus §4 regression loop — The plan batches weeks of safety, instruction, verification, memory, and retrieval changes before the scheduled baseline rerun, then demands attribution of each gain. That cannot isolate individual effects and contradicts the prescribed fix→regression cycle — `review/guide-v260411.txt`, §10: “If everything moves at once, you can’t tell which change had an effect”; its regression step returns to trace analysis after each improvement round.

- [SEVERITY: medium] §6 reference scaffold versus A4, A6, and decision rule 6 — The recommended starting scaffold does not satisfy the document’s mandatory safety floor, verification gate, or run-level malformed-response and wall-clock caps. The missing integration work is not identified — `review/paper-2609.00006.txt`, Listing 3 line 78 returns immediately when there are no tool calls; its caption explicitly says “Illustrative scaffold, not production code.”

## D. OPERATIONAL WEAKNESS

- [SEVERITY: medium] A7 and decision rule 5 — “Fixed buffer” gives no buffer calculation, while “last ~30%” does not specify tokens, messages, or turns. The source implementations use materially different units and reserves; 30% is one implementation choice, not a validated universal optimum — `review/paper-2609.00006.txt`, §9.5 gives Gemini’s 30% history tail, Pi’s “20K recent,” and OpenCode’s “two user turns”; Listing 3 calculates `len(self.messages) * 0.30`.

- [SEVERITY: medium] Decision rules 2 and 6 — “Delete-test passes,” “makes it noise,” and “nothing heavier until measured” lack acceptance criteria. The stuck-detection rule also leaves the malformed-response limit, runtime cap, and unattended handling of “ask” undefined — `review/paper-2609.00006.txt`, §6.2 says OpenCode leaves the repetition decision to the user, while §10.9 says its headless runs “auto-reject all asks.” Those are different operating contracts.

- [SEVERITY: high] §4 baseline/regression steps; §7 exit criterion — Reusing the same task set and having a human “confirm no overfit” does not define an overfitting check. There is no held-out regression requirement, tolerated regression, target success rate, or deployment acceptance condition; the exit criterion can be met with poor measured performance — `review/guide-v260411.txt`, §10 requires preventing “overfitting to specific tasks causing regression elsewhere”; `review/paper-2609.00006.txt`, §15.5 explicitly includes a fixed task distribution, fixed model, and “target success rate p.”

- [SEVERITY: medium] Decision rule 10 — The reasoning schedule has no task-budget condition or mechanism for identifying planning, implementation, and verification transitions. Its evidence comes from timed benchmark tasks, so it should be a tested default rather than a universal allocation rule — `review/guide-v260411.txt`, §10: “Each task has a time limit”; full-xhigh lost because “many tasks ran out of time before completion.”

- [SEVERITY: medium] §7 scope and mandatory migrations — Coding, operations, and research harnesses receive the same tool, retrieval, memory, and orchestration prescriptions without domain-specific evidence. The paper explicitly scopes its recommendations to coding agents and says retrieval conclusions are domain-specific — `review/paper-2609.00006.txt`, §16 addresses “an engineer designing a new coding agent”; §13.2: “The reasons are domain-specific.”

## E. SOURCE DISAGREEMENTS AND THEIR RESOLUTION

- [SEVERITY: high] A6, A9, decision rule 7 — The document does not correctly resolve the multi-agent tension. Both sources favor starting simple, but G additionally endorses independent implementation, writer/reviewer sessions, and full-stack Planner/Generator/Evaluator workflows; P Recommendation 12 gives a narrower exploration trigger. The $9/$200 example establishes neither universal multi-agent necessity nor a cost-matched architecture advantage: elapsed time changes from 20 minutes to six hours — `review/guide-v260411.txt`, §17 recommends those separate scenarios and reports both time/cost pairs; `review/paper-2609.00006.txt`, §16.7 requires “a concrete breadth-first exploration phase.”

- [SEVERITY: medium] A3 versus A2 — The categorical framework ban leaves an empirical tension unresolved: G’s strongest harness-improvement example is LangChain, while P itself describes LangChain’s Deep Agents harness as built on LangGraph. The corpus’s zero-framework count is not evidence that this competing approach cannot work — `review/guide-v260411.txt`, §10 reports 52.8%→66.5%; `review/paper-2609.00006.txt`, §14.2 identifies “LangChain’s harness on LangGraph” and says both directions converge on the same artifact shape. Selecting hand-written loops as a default is supported; presenting that selection as a universally settled conclusion is not.

- [SEVERITY: medium] A12 — The subtraction pass is a reasonable partial resolution, but “as the model improves, the harness thins” conflates removal of model-compensating scaffolding with total runtime size. G emphasizes the former; P documents simultaneous growth in safety, integration, memory, and platform infrastructure — `review/guide-v260411.txt`, §05: “As the model gets stronger, the harness should get thinner”; `review/paper-2609.00006.txt`, §14.5: “Codex’s workspace nearly doubled … in one quarter.” The document should distinguish these two kinds of change.

- [SEVERITY: low] A4, A8, A12 — Preferring P’s July inventory over G’s April inventory is appropriate, but the conflicting snapshots are not explicitly reconciled. Dating claims should also identify which earlier claims are superseded — `review/guide-v260411.txt`, §15 says “Codex CLI doesn’t have hooks,” and §16 lists no Codex automatic memory; `review/paper-2609.00006.txt`, §10.2 describes lifecycle hooks and §9.6 an autonomous memory pipeline.

VERDICT: REVISE
The document captures many source recommendations accurately, but its factual conflicts, overgeneralized prescriptions, contradictory verification policy, and incomplete operating criteria prevent acceptance as a dependable foundations document.
